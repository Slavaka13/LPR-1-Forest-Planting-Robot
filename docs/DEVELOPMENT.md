# Среда разработки и порядок внесения изменений

## Разделение трёх уровней программного обеспечения

1. **Raspberry Pi:** основная Python-программа и диагностические инструменты в `raspberry-pi/`.
2. **STM32:** FOC-прошивка и зависимости в `firmware/source/`; модификации аппаратной логики могут требовать перепрошивки.
3. **Инженерные материалы:** документация, схема и CAD-модели. Крупные STEP-файлы в текущем Git-репозитории могут отсутствовать.

## Среда Raspberry Pi

Требуется Linux и Python 3, доступ к I²C, UART и USB. По импортам кода используются, в частности, `pyserial` (`serial`), `smbus2`, `lgpio`; системные утилиты включают `ffmpeg`, `systemctl --user`, `vcgencmd`, `ssh/scp`, `journalctl` в соответствующих сценариях. Это **перечень зависимостей по исходникам**, а не доказательство совместимости с любой версией библиотек.

Точные версии пакетов, образ ОС, правила доступа к GPIO/USB и полный reproducible lock-файл в исходном комплекте не представлены. Не создавайте фиктивный `requirements.txt` с произвольными версиями: сначала зафиксируйте рабочее окружение с реально действующего Raspberry Pi.

## Работа без оборудования

Из каталога `raspberry-pi/`:

```bash
python3 -m compileall -q .
python3 test_modules.py
python3 test_gps_log.py
```

Эти команды прошли на контрольной копии файлов 24.10.2026. Успешный прогон не гарантирует функционирование двигателей.

## Сборка STM32

В исходном дереве есть `Makefile`, `platformio.ini`, `MDK-ARM`, `STM32F103RCTx_FLASH.ld`. Они относятся к FOC-прошивке конкретной платы; без проверки `config.h`, выбранного варианта платы и назначения выводов **запрещено прошивать контроллер наугад**. Документы upstream-проекта см. в `firmware/source/README.md` и `firmware/source/LICENSE`.

## Работа с Git

- `main` — контрольная ветка защиты: изменения документации делать отдельными коммитами.
- Перед изменением алгоритмов создать отдельную ветку, зафиксировать исходные параметры и план отката.
- В коммите изменения кода прикладывать результаты программных тестов.
- Изменения в управлении приводами, аварийных остановках, токовых порогах и питании проверять на стенде.
- Не коммитить реальные координаты, журналы с личными данными, ключи SSH, пароли и приватные токены.

## План релиза

После проверки полноты документов, исходников, авторских прав, схем, результатов тестов и согласования состава комплекта можно подготовить помеченную версию для комиссии. До завершения аудита не следует создавать релиз с названием «проверено в полевых условиях».
